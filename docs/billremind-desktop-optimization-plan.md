# BillRemind 桌面端优化方案

> 文档版本：v1.0  
> 适用范围：BillRemind 插件桌面端 UI、业务实现、数据模型、可靠性与测试  
> 明确不包含：移动端响应式布局、移动端表格改造  
> 基于代码版本：当前工作区 `D:\Codex\tools\BillRemind`

## 1. 文档目标

本方案不以“增加更多功能”为出发点，而是从插件的核心任务倒推设计：

> 用户需要可靠地知道下一次账单、还款和年费事项，并在真正需要处理时快速完成操作，同时不能因为插件、并发或误操作丢失账单数据。

因此优化目标按以下顺序排列：

1. 时间计算和逾期状态必须正确。
2. “需要处理”和“未来会发生”必须清晰区分。
3. 数据变更必须可追踪、可恢复、不会被并发覆盖。
4. 桌面端必须能完成添加、查看、编辑、删除和提醒配置的主要闭环。
5. UI 要降低认知负担，而不是只增加装饰。

## 2. 当前实现概况

当前插件已经具备较好的基础分层：

- Host 入口和 HTTP 路由：`index.js`
- JSON 文件持久化：`store.js`
- 日期和业务服务：`service.js`、`dates.js`
- Agent 工具：`tools.js`
- Web 客户端面板：`client.js`
- 中英文元数据：`locale/zh.json`、`locale/en.json`

当前核心流程是：

```text
UI / Agent
   ↓
HTTP 路由或工具参数转换
   ↓
BillService
   ↓
Store
   ↓
state.json
```

这个结构可以继续使用，不建议为了本次优化整体重写。重点是统一业务语义、补齐数据保护和减少 UI/服务端各自判断造成的不一致。

## 3. 当前问题与影响

### 3.1 高优先级问题

#### A. 新增卡片不检查别名唯一性

`service.js` 的新增流程直接将卡片加入数组，而按别名查找时只返回第一张匹配卡片。结果是同名卡片可能导致 Agent 更新、删除或设置提醒时操作错误对象。

影响：数据管理不可预测，属于高风险正确性问题。

#### B. 持久化只有进程内串行，没有跨进程保护

`store.js` 的 Promise 队列只能保护同一个 Store 实例。多个进程或多个宿主实例同时执行读-改-写时，后写入者可能覆盖先写入者的业务修改。

影响：数据文件仍然是原子写入，但业务更新可能丢失。

#### C. JSON 读取失败时静默重置为空状态

当前解析失败会回退到初始 seed。损坏文件、短暂 I/O 失败或外部并发读取异常都会表现为“暂无卡片”，后续写入还可能覆盖原始数据。

影响：账单数据可能不可逆丢失，且用户无法知道发生了什么。

#### D. Web 清空接口缺少确认保护

Agent 工具要求 `confirm=true`，但 Web 路由的 `clear` 操作直接调用清空服务，导致两个入口的安全语义不一致。

影响：任何已通过同源鉴权的客户端请求都可能清空全部数据。

#### E. 逾期账单会显示成“今天”

当前 `days <= 0` 的显示逻辑把负数和 0 混为一类。逾期 5 天的账单可能被 UI 显示为“今天”，而 Agent 输出又可能显示“还剩 -5 天”。

影响：会直接误导用户判断还款状态。

#### F. 提醒窗口和近期节点语义混淆

服务端将未来 30 天的所有节点放入 `upcoming`，但 Agent 会额外标记 `remind`，UI 却不展示该标记。用户无法区分“需要现在处理”和“只是近期会发生”。

影响：提醒信息噪声过大，真正紧急事项不突出。

### 3.2 中优先级问题

- 全局提醒设置会覆盖所有已有卡片的个性化提醒值。
- 日期计算完全依赖 Host 本地时区，没有明确的用户时区策略。
- 31 日在短月份按月末处理，但 UI 没有解释这一规则。
- 迁移数据只检查 `id`，没有完整校验卡片字段和提醒范围。
- Agent Markdown 未对别名中的 `|`、换行和反引号进行转义。
- 客户端定时刷新、可见性刷新和保存后的刷新可能发生竞态。
- 客户端使用相对接口 URL，在非根路径宿主页面下可能请求错误地址。

### 3.3 桌面端 UI 问题

- 没有“添加卡片”入口，空状态要求用户转到聊天。
- 没有提醒设置入口，后端能力无法被发现。
- 编辑弹窗使用 `alert()`，没有字段级错误。
- 保存期间没有 loading 和重复提交保护。
- 弹窗缺少 `role="dialog"`、`aria-modal`、Esc 关闭和焦点管理。
- 点击遮罩会直接关闭，可能丢失未保存内容。
- “本期账单”“下一次还款”“需要处理”之间层级不够清晰。
- 桌面宽屏表格可以保留，但需要强化排序、状态和操作层级。

## 4. 目标状态模型

### 4.1 卡片数据模型

建议将提醒天数改成“可继承默认值”的模型：

```json
{
  "version": 2,
  "revision": 12,
  "timezone": "Asia/Shanghai",
  "defaults": {
    "repayAdvanceDays": 3,
    "annualAdvanceDays": 30,
    "statementAdvanceDays": 0
  },
  "cards": [
    {
      "id": "card_xxx",
      "alias": "招行 Visa",
      "last4": "8888",
      "statementDay": 15,
      "repaymentDay": 25,
      "annualFeeMonth": 8,
      "annualFeeDay": 15,
      "repayAdvanceDays": null,
      "annualAdvanceDays": 30,
      "statementAdvanceDays": null,
      "billAmount": 1234.56,
      "createdAt": "2026-11-10T02:00:00.000Z",
      "updatedAt": "2026-11-10T02:00:00.000Z"
    }
  ]
}
```

约定：

- `null` 表示继承全局默认值。
- 非 `null` 表示卡片级覆盖。
- `revision` 用于并发更新检测。
- `timezone` 明确日期计算所属时区。
- `updatedAt` 用于显示和排查，而不是只保留 `createdAt`。

### 4.2 统一状态模型

服务层统一返回节点状态，UI 和 Agent 不再自行推断：

```json
{
  "type": "repayment",
  "date": "2026-11-15",
  "days": -2,
  "status": "overdue",
  "isReminder": true,
  "reminderDays": 3
}
```

`status` 建议只有以下几种：

- `overdue`：日期已过，`days < 0`
- `today`：今天，`days === 0`
- `remind`：尚未到期但已进入提醒窗口
- `upcoming`：未来会发生，但尚未进入提醒窗口

显示规则：

```text
days < 0  → 已逾期 N 天
days = 0  → 今天
days > 0  → 还有 N 天
```

### 4.3 近期区域分层

桌面端首页建议改为：

```text
需要处理
  已逾期
  今天
  已进入提醒窗口

未来安排
  未来 30 天内但尚未进入提醒窗口

全部卡片
  宽表格
```

这样“近期到期”不再承担两个含义。

## 5. 桌面端 UI 方案

### 5.1 顶部概览

顶部保留标题和副标题，下方增加统计摘要：

```text
需要处理  2    逾期 1    今天 1    卡片总数 4
```

统计项点击后可筛选对应内容。

右侧提供主要操作：

- 添加卡片
- 提醒设置
- 刷新
- 更多操作：导出、清空数据

### 5.2 “需要处理”区域

每条提醒显示：

```text
[状态] 招行 Visa · 还款日
2026-11-15 · 已逾期 2 天
本期账单 ¥1,234.56
[编辑]
```

交互要求：

- 逾期使用错误色，并显示具体逾期天数。
- 今天使用醒目但不等同于错误的状态色。
- 即将到期显示提醒天数。
- 点击条目可以直接打开对应卡片编辑弹窗。
- 未录入金额时显示“金额未录入”，同时提供快速录入入口。

### 5.3 全部卡片宽表格

桌面端继续使用表格，不进行移动端布局改造。建议列顺序调整为：

| 卡片 | 本期账单 | 下一次还款 | 账单日 | 年费日 | 提醒设置 | 操作 |
| --- | --- | --- | --- | --- | --- | --- |

原因是“本期账单”和“下一次还款”是用户最常处理的信息，应放在前面。

建议支持：

- 按紧急程度排序；
- 按卡片名称排序；
- 只看需要处理；
- 只看未录入金额；
- 表头固定；
- 状态徽标；
- 快速编辑金额；
- 编辑和删除按钮保持明确的主次关系。

### 5.4 添加/编辑表单

表单分为三组：

#### 基本信息

- 卡片别名，必填且唯一；
- 尾号后 4 位，可选。

#### 日期信息

- 账单日；
- 还款日；
- 年费月份；
- 年费日期。

在日期字段旁说明：

> 选择 31 日时，短月份按当月最后一天计算。

#### 提醒与账单

- 本期账单金额，可为空；
- 还款日提前提醒天数；
- 年费提前提醒天数；
- 账单日提前提醒天数。

每个提醒字段提供“继承全局默认”选项。

表单行为：

- 使用字段级错误，不使用 `alert()`；
- 保存期间禁用表单和按钮；
- 支持 Enter 保存；
- Esc 关闭；
- 有未保存修改时关闭前确认；
- 保存成功后关闭并定位到刚修改的卡片；
- 服务端错误显示在表单顶部，同时保留用户输入。

### 5.5 危险操作

删除单卡片：

- 首次点击弹出确认；
- 删除成功后显示 Toast；
- 提供 5 秒撤销。

清空全部：

- 放在“更多操作”中，不放在主操作区；
- 先导出或提示备份；
- 要求输入明确短语；
- 服务端必须验证确认参数；
- 清空前生成备份。

## 6. 服务端与 API 方案

### 6.1 操作协议统一

UI 和 Agent 最终都应调用相同的服务方法，参数名称统一使用 camelCase，避免 UI 层先使用 snake_case、再由客户端转换。

建议接口：

```text
GET  /billremind/state
POST /billremind/cards
PATCH /billremind/cards/:id
DELETE /billremind/cards/:id
PATCH /billremind/settings
POST /billremind/clear
POST /billremind/export
```

如果暂时保留 `/ops` 单接口，也必须统一以下规则：

- 所有变更返回新的 snapshot 和 `revision`；
- clear 必须显式确认；
- 错误返回稳定的 `code` 和字段信息；
- 不把底层文件错误原样暴露给客户端。

### 6.2 并发控制

推荐使用版本号：

```text
客户端提交 revision=12
服务端当前 revision=13
→ 返回 409 VERSION_CONFLICT
```

客户端收到冲突后：

1. 保留用户正在编辑的内容；
2. 加载最新数据；
3. 提示用户选择覆盖或重新编辑。

如果运行环境允许文件锁，则同时增加跨进程锁，避免两个进程同时写入。

### 6.3 存储错误处理

区分以下情况：

- 文件不存在：创建初始状态；
- JSON 损坏：保留原文件并进入错误状态；
- 权限错误：显示存储不可用；
- 并发版本冲突：重读并重试或返回冲突；
- 写入失败：保留临时文件并报告失败。

禁止把所有读取异常统一转换为空卡片。

### 6.4 输入和输出安全

服务端统一校验：

- 别名不得包含控制字符和换行；
- 卡片别名规范化后必须唯一；
- 日期、金额和提醒范围统一校验；
- 迁移数据使用同一套 schema 校验；
- Agent Markdown 对 `|`、反斜杠、换行和反引号进行转义。

## 7. 日期与账单周期方案

### 7.1 时区策略

默认时区设为 `Asia/Shanghai`，并在状态文件保存。所有日期计算使用同一时区，不依赖 Node 进程的本地时区。

如果未来支持多用户或跨时区，再将时区加入设置页面。

### 7.2 账单周期

不要只把账单日、还款日作为三个互相独立的节点。至少在服务层构造：

```text
当前账单周期
  出账日期
  对应还款日期
  账单金额
  还款状态
```

同时保留下一次账单日、下一次还款日和下一次年费日作为未来节点。

### 7.3 边界规则

必须明确并测试：

- 31 日遇到 2 月、4 月、6 月、9 月、11 月；
- 2 月 29 日；
- 账单日大于还款日时的跨月规则；
- 今天正好是节点日期；
- 还款日过去后的逾期显示；
- 年末跨年；
- Host 时区与配置时区不同的情况。

## 9. 分阶段实施计划

### Phase 0：建立保护网

目标：不改变主要 UI，先避免数据和状态错误。

任务：

- 增加测试框架和日期测试；
- 修复逾期显示；
- 修复相对 API URL；
- 新增别名唯一性检查；
- HTTP clear 增加确认；
- Agent Markdown 转义。

验收：

- 逾期不会显示成今天；
- 重复别名无法创建；
- 未确认不能清空；
- 非根路径下 UI 仍能加载。

### Phase 1：修复数据模型和持久化

任务：

- 引入 `revision`；
- 设计跨进程锁或版本冲突机制；
- 损坏文件隔离和备份；
- 提醒字段支持继承默认值；
- 增加迁移校验；
- 明确时区字段。

验收：

- 并发修改不会静默覆盖；
- 损坏数据不会被当成空数据覆盖；
- 全局设置不会破坏单卡设置。

### Phase 2：完成桌面端功能闭环

任务：

- 添加卡片按钮和表单；
- 全局和单卡提醒设置；
- 需要处理 / 未来安排分区；
- 表格排序、筛选和状态徽标；
- 快速录入本期账单金额；
- 保存状态和统一错误展示。

验收：

- 用户无需进入聊天即可完成核心卡片管理；
- 所有提醒状态与 Agent 输出一致；
- 用户可以明确知道下一步要处理什么。

### Phase 3：恢复能力和可观测性

任务：

- 导入/导出；
- 操作日志；
- 删除撤销；
- 备份清理策略；
- 存储和 API 错误诊断。

验收：

- 数据误删可恢复；
- 能追踪一次变更来自 UI 还是 Agent；
- 文件错误有明确提示和诊断信息。

## 10. 暂不做的事项

本轮明确不做：

- 移动端表格改为卡片布局；
- 移动端专属交互；
- 多用户云同步；
- 自动从银行或短信读取账单；
- 复杂账单分期和消费分类；
- 多币种账单。

这些功能需要不同的数据模型和产品决策，不应混入当前桌面端可靠性优化。

## 11. 最终验收标准

当以下条件全部满足时，可认为本轮优化完成：

- 逾期、今天、提醒中、未来四种状态显示一致；
- UI、Agent 和服务层使用同一套状态模型；
- 新增卡片不能产生重复别名；
- 全局提醒设置不会静默覆盖单卡配置；
- 清空操作在所有入口都需要明确确认；
- 存储损坏不会静默显示为空并覆盖原数据；
- 并发写入有锁或版本冲突保护；
- 桌面端可以独立完成添加、编辑、删除和提醒设置；
- 日期边界和金额规则有自动化测试；
- 文档和代码中的时区、31 日处理规则保持一致。

## 12. 推荐首批改动清单

如果只能先做一小批改动，建议按以下顺序：

1. 修复 `days <= 0` 被显示为“今天”的问题。
2. 将客户端 API 改为根路径或宿主注入基址。
3. 新增卡片时复用唯一别名检查。
4. 给 Web clear 增加显式确认。
5. 将 `upcoming` 拆成“需要处理”和“未来安排”。
6. 修复全局提醒覆盖单卡提醒的行为。
7. 为 Store 增加损坏文件隔离和版本检查。
8. 增加桌面端“添加卡片”和“提醒设置”。
9. 用字段级错误替换编辑弹窗中的 `alert()`。
10. 为日期、逾期和并发写入补自动化测试。

## 13. 当前实施状态（更新于 2026-11-11）

本节记录方案执行后的实际状态，避免“设计目标”和“已经完成”混淆。

### 13.1 已完成

已落地的桌面端和可靠性改动包括：

- 逾期、今天、提醒中、未来状态已统一建模；
- 逾期账单不再显示为“今天”；
- 新增卡片增加规范化后的别名唯一性检查；
- Web 清空操作要求显式 `confirm=true`；
- JSON 状态损坏不再静默重置为空数据；
- Agent Markdown 输出增加特殊字符转义；
- 客户端 API 使用根路径，避免非根路由解析错误；
- 客户端刷新增加请求序列保护；
- 桌面端已增加添加卡片入口；
- 单卡编辑已支持还款日和年费提前提醒天数；
- 桌面端已增加全局提醒设置入口，并支持保存中禁用和未保存修改确认；
- 编辑弹窗已增加基本无障碍语义、自动聚焦、Esc 关闭和字段错误区域；
- Store 已增加跨进程目录锁和 `revision` 版本号；
- revision 已贯穿 Service、Web ops 和 Agent 工具，过期写入返回 `409 VERSION_CONFLICT`；
- 桌面端已保留冲突表单，并提供重新加载/确认覆盖路径；后端已支持 `force=true + force_confirm=true` 的显式覆盖闭环；
- Service 清空操作增加二次确认边界，不能绕过入口直接清空；
- 日期计算已固定使用 `Asia/Shanghai` 日历语义；
- 已增加重复别名、逾期、时区、并发新增、损坏文件、Markdown 转义和备份恢复安全测试；
- 已增加备份导出/导入 API，导入执行严格 envelope 校验、重复 ID/别名校验、原子写入、revision 单调递增和原型污染防护；
- force 覆盖已增加独立测试，未提供二次确认时仍拒绝覆盖；
- 删除已增加持久化 trash tombstone、一次性恢复 token、过期检查、原 ID/别名冲突检查和 restore 服务能力；Web remove 响应已返回 token/过期时间，桌面 Undo 通过 restore API 恢复原卡；
- reminder provenance 已进入服务端：inherit/custom 会影响有效提醒计算，旧卡缺来源时保守视为 custom；
- Store 锁已增加心跳续租，长事务不会因固定 30 秒阈值被误抢占。
- 桌面端已增加提醒来源的保守标识，但服务端尚未提供 provenance 字段，无法区分“显式自定义但恰好等于默认”和真正继承。

### 13.2 尚未完成的任务

#### P0/P1：建议优先继续处理

1. **冲突后的恢复操作**

   revision 冲突检测已贯穿 Store、Service、Web ops、Agent 工具和桌面端编辑请求。尚未完成的是冲突后的“重新加载/覆盖”交互：当前已能保留表单内容并展示错误，但还没有结构化的冲突对比和恢复按钮。

2. **全局提醒设置的继承标识**

   桌面端已有全局提醒设置入口，但单卡页面尚未明确标记某个值是“继承全局默认”还是“卡片自定义”。

3. **未保存修改保护的自定义确认框**

   当前已实现 dirty state 和取消/Esc 确认，但仍使用浏览器确认框，尚未统一为主题化、可读屏的自定义确认弹窗。

4. **删除撤销**

   当前删除依赖确认后立即执行，没有 Toast、Undo 或软删除回收站。

#### P1：数据恢复与可观测性

5. **备份管理体验**

   已提供 JSON 备份导出/导入 API，但尚未提供桌面端下载、导入预览、备份列表、自动旧版本备份和一键回滚入口。

6. **操作日志**

   当前只记录卡片创建和更新时间，尚未记录 UI/Agent 来源、修改字段、删除前内容和清空事件。

7. **锁机制专项测试和诊断**

   当前已实现目录锁和 30 秒过期清理，但还需要覆盖残留锁、锁超时、进程中断和写入中断场景，并在 UI 中展示更明确的“数据正在被其他进程修改”提示。

#### P2：桌面端体验和工程质量

8. **未来安排区域**

   当前主区域聚焦“需要处理”，未来 30 天内但尚未进入提醒窗口的节点还没有独立的“未来安排”区域。

9. **桌面表格增强**

   尚未完成按紧急程度排序、只看需要处理、只看金额未录入、固定表头、状态筛选和本期金额快速编辑。

10. **HTTP 与 UI 集成测试**

    当前已有服务层和存储层行为测试，但还缺少路由级测试、清空确认测试、UI 添加/编辑/错误/重复提交测试和版本冲突测试。

11. **实际 Web GUI 验收**

    当前已完成语法、Node 行为和不同 Host 时区下的测试，但还没有在实际 DSH Web GUI 中完成视觉和交互验收。
